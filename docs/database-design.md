# Database design

## Conventions

PostgreSQL on Cloud SQL. UUID primary keys generated server-side. Mutable rows carry `created_at`, `updated_at` (`timestamptz`, UTC), nullable actor IDs for system/import operations, and integer `version` for optimistic concurrency. Use `text` plus `CHECK` constraints for domain statuses, mapped to typed C# enums; this is easier to evolve than PostgreSQL enums. Index all foreign keys. Do not store generation, siblings or marital status.

Birth and death may be approximate: `birth_year`, `birth_month`, `birth_day` and corresponding death parts, nullable, with constraints requiring year before month and month before day. Validate actual calendar dates in the application and database where feasible. Never fabricate January 1 for an unknown month/day.

`family_persons` and `family_memberships` intentionally answer different questions. A person may be in several families without an account, and a user may join several families before a claim is approved. `relationship_approvals` rows are generated for all families affected by a cross-family edge. The publishing transaction checks the complete required set and reviewer authority.

## Name-history constraints, search and migration

`person_names` is the source of truth for current and former names; do not keep `persons.full_name` as a second mutable copy. Use `name_type IN (UNSPECIFIED,LEGAL,BIRTH,PREFERRED,ALIAS)`. `FORMER` is represented by `is_current = false`, independent of type. `full_display_name` is stored verbatim for rendering and is not reconstructed from components. `first_name`, `middle_name` and `last_name` are optional even when a full display name exists. `notes` are reviewer-only and length-limited.

Create a partial unique index on `(person_id) WHERE is_current AND is_primary` to allow at most one current primary. Exactly one current primary for every nonarchived Person is a transaction-level invariant: create Person and first name together, and serialize a primary-name change while closing the prior primary row. Keep a `(person_id, is_current, effective_from DESC, id)` history index. No uniqueness constraint on spelling: a Person may reuse a name later. Effective dates can be null; a former row may have unknown `effective_to` rather than an invented date.

For family-scoped search, join authorized `family_persons` to `person_names` whose effective visibility permits the caller. Match normalized `full_display_name` across current and former records, plus an authorized family display alias. Return distinct Person IDs, rank a current-primary match before a former match, and show the current permitted display name in the result. A former-name match may be disclosed as a match hint only if that name itself is visible. Start with exact/prefix matching and an expression index on normalized display text; evaluate trigram/locale-aware matching against representative Thai and other target-language names before choosing a fuzzy-search index. Query plans must keep family and visibility filters effective before any result is returned.

For the initial schema, create `person_names` beside `persons`, require creation of a first current primary name in the same transaction, and omit `persons.full_name`. If an earlier schema is deployed, add `person_names`, backfill one current primary row from every existing `persons.full_name`, validate counts and nonblank values, switch API reads/writes, then drop `persons.full_name` only in a later reviewed migration with backup/rollback guidance. Do not discard existing names during deployment. Audit `NAME_ADDED`, `PRIMARY_NAME_CHANGED`, `NAME_CORRECTED` and visibility changes using IDs and redacted metadata; the name rows themselves preserve history without copying sensitive spellings into general logs.
## Relationship integrity

`PARENT_CHILD` means `person_a_id` is parent and `person_b_id` is child, with kind `BIOLOGICAL`, `ADOPTIVE` or `STEP`. `UNION` means `person_a_id < person_b_id`, with kind `MARRIAGE` or `PARTNERSHIP`. Add `CHECK` constraints for these shapes, status and date combinations, nonnegative photo sizes and valid partial dates. A partial unique index on `(person_a_id,person_b_id,kind)` where `type = PARENT_CHILD AND status = ACTIVE AND ended_on IS NULL` rejects duplicate currently effective parent links. Publication status and temporal validity are separate: an ended union retains `status = ACTIVE` as a published historical fact. Active union episodes for the same pair and kind cannot overlap; enforce transactionally under a lock, or use a PostgreSQL exclusion constraint after interval semantics are settled. Historical ended episodes remain.

Cross-row invariants such as parentage cycles, complete relationship approvals and at least one active Creator per family need a transactionally locked service operation or trigger. Family creation inserts its active creator membership, Creator and FamilyAdmin assignments, and audit event with the Family in one transaction. Test concurrent requests. No person, family or user cascades into kinship, membership or audit rows; use reviewed archival and erasure processes. Do not add a guardian-account ownership table for Phase 1. Minor status may be inferred from known birth information for protective policy, but incomplete dates must take the safer path; exact age rules remain a product decision.

## Queries and migration

Use `WITH RECURSIVE` for ancestors, descendants and graph expansion, with explicit depth limit, visited-path cycle detection and result cap. Traverse relationships both ways for kinship but preserve parent direction. Index both endpoints. Authorize nodes and fields before returning results; reachability is not permission. Cursor-paginate lists and never default to a whole-family graph. Use transactions for approvals, role changes, relationship publication and photo finalization.

Migration order: (1) users and audit infrastructure before exposing mutations; (2) families, memberships, grants and review workflows; (3) persons, person_names and family associations; (4) basic same-family relationships for Phase 1; (5) relationship approvals with cross-family publication and photos in later phases. Review migrations with restore guidance and test on realistic data. [PostgreSQL recursive query documentation](https://www.postgresql.org/docs/current/queries-with.html) describes cycle detection.

Milestone 2 creates only `users` and `audit_events`; the nullable `audit_events.family_id` column receives its Family foreign key when `families` is migrated in Milestone 3. The Milestone 1 migration contains no business rows, so this migration has no backfill. Keep existing databases and apply the new migration in place; do not recreate them to add these tables.

The follow-up Milestone 2 migration installs PostgreSQL triggers that reject UPDATE, DELETE and TRUNCATE on `audit_events`, including direct SQL that bypasses EF Core. INSERT remains available to the audit writer. A deployed API should use a non-owner database role granted only the required application privileges; table owners can alter triggers, so the migration does not replace deployment role separation.
